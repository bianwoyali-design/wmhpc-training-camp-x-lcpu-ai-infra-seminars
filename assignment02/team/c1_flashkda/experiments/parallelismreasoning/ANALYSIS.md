# 讨论点 3：状态依赖下的并行度候选与反例

**优先考虑独立序列/head 和 value 维拆分。** 多 head 放进一个 CTA 可以改善 CTA 内利用率，
但会减少可分配到 SM 的 CTA；persistent 调度不能凭空增加独立状态链；2-CTA 能扩大一个任务
占用的硬件范围，却不消除 chunk 依赖。只有改变递推组织（例如 affine scan）才能真正并行
时间维，代价是额外工作量、存储与舍入路径变化。

## 1. 先确认官方已经做了什么

[launch](../../FlashKDA/csrc/smxx/fwd_launch.cu) 的两个 grid 不同：

- K1：`grid=(total_tiles,H)`，不同 chunk/head 可独立准备。
- K2：`grid=(N,H)`，每个 CTA 处理一个 sequence/head，循环 `ceil(seq_len/16)` 个 chunk。

[K2](../../FlashKDA/csrc/smxx/fwd_kernel2.cuh) 为 192 线程：四个计算 warp，一个加载 warp，
一个存储 warp；三层输入、两层输出流水。状态在 CTA 的 shared memory 中跨 chunk 保留，
计算过程中使用寄存器 fragment。每个计算 warp 已负责两个 16-column value 块。
因此沿着一条状态链常驻、循环和预取已经存在；它不是每个 chunk 发一次独立 kernel。

这里区分两种常被叫作 persistent 的结构：

1. **状态链常驻**：一个 CTA 做完整 sequence/head，官方已有。
2. **固定 worker 池**：少量 CTA 从队列领取多条状态链，官方没有显式软件任务队列。

后者可能减少调度开销或支持特定排序，但 CUDA 本来就会在有资源时分配待运行 CTA。
不能拿一个低效的静态轮转队列当作官方 baseline，进而宣称软件动态队列必然更快。

## 2. 可分维度与必须保留的依赖

采用朴素参考的逻辑状态布局 S[K,V]（官方外部状态布局为 [V,K]）：

```
Sbar = diag(exp(g_t)) S_{t-1}
u_t  = v_t - k_t^T Sbar
S_t  = Sbar + beta_t k_t u_t^T
o_t  = scale q_t^T S_t
```

由此可得：

- 不同 sequence/head 的状态完全独立，能够分配给不同 CTA。
- 不同 **value 列**只依赖自己的状态列与 v 分量，可分别完成整条递推，不需要跨分区归约。
- **key 行**参与 `k^T S` 和 `q^T S` 的归约；独立更新各半行会丢失跨分区预测项。
- chunk/token 的先后依赖真实存在；下一段需要上一段最终状态，不能直接重置。

对 [提供的朴素参考](../../fla_kda_ref/naive.py) 做三种子、非零初态检查，结果见
[algebra.csv](results/algebra.csv)：value 拆分 2/4/8 份与 head 分组保持结果；
时间分段传递状态也保持结果。具体误差和反例列在后面的实测证据中。

## 3. 候选方案逐项找反例

### A. 增加独立 sequence/head

这是最直接的跨 SM 并行来源。若每卡 head 数为 H，独立序列数 N，则 K2 有 NH 个 CTA。
B300 的 148 个 SM 上，N=1、H=12 的 SM 覆盖率上界仅 12/148=8.1%；H=96 为 64.9%。
这里是覆盖上界，不是测得的 occupancy，也不保证 CTA 被均匀分配。

**反例：**把一条 8192-token 序列人为变成八条 1024-token 独立序列，会重置七次状态。
它能增加任务数，但不是等价优化。合法途径是服务端合批多个真实独立请求，而不是切断上下文。

### B. 多 head 放入同一个 CTA

设每 CTA 合并 G 个 head，CTA 数从 NH 变为 `N ceil(H/G)`。
好处可能是减少任务调度、增加 CTA 内工作量、复用控制流程；若任务很多、每个很短，值得测试。

**反例一：缺任务时越合并越少。** N=1、H=12、G=4，只剩 3 个 CTA，覆盖上界降到 2.0%；
H=96 也只剩 24 个 CTA。填满一条大 MMA 的局部收益不能自动补偿空闲 SM。

**反例二：head 不共享右操作数。** 对四个 Gram `A_h B_h`，把 A 沿 M 拼起来并使用 B_0，
后三个 head 会算错。若拼成 `A_stack B_stack` 的 64×64 Gram，只有四个 16×16 对角块有用，
其余 12 个跨 head 块是无用算术：有效输出仍只有 25%。
长方形状态投影也不能假设四个 head 共享状态矩阵。可以把 head 做成独立批次、warp 分工或
合适的块对角布局，但这些都需要另行量化，而不是“拼上 M 就消灭 padding”。

**反例三：资源增长。** 一份 BF16 128×128 状态为 32 KiB。官方一份完整 K2 CTA 的动态
shared footprint 实测为 98432 B；若直接复制现有缓冲，G=2/4 需要约 192.25/384.5 KiB。
必须重新设计流水和缓冲生命周期，不能假定合并 head 后仍保有原驻留数量。

### C. 拆 value 维：把一条状态链分给多个独立 CTA

S 分成 P 个 value 列块，CTA 数增为 NHP，理想每个 CTA 的状态/输出工作量约为原来的 1/P。
它不需要在每个 chunk 间交换状态；每个分区只接续自己的列。
这与原 kernel 的 warp 内 value 分工不同：现在把分区放到可以分配到不同 SM 的 CTA。

N=1、H=12：P=2/4/8 对应 24/48/96 个 CTA，覆盖上界 16.2%/32.4%/64.9%。
H=96、P=2 已有 192 个 CTA，但仅据任务数不能预测延迟收益。

**反例：输入重复和小 tile。** q/k/gate/INV/Mqk 在 value 分区间共享其数学值，独立 CTA
可能重复加载这些数据。按当前 K2 的 TMA payload，每 chunk/head：

- v：4096 B，可按 value 分区。
- k_decayed/q_decayed/k_restored：12288 B；g_total：512 B；INV/Mqk：1024 B；beta：64 B。
  共 13888 B，在这种简单拆分中每个分区都需要。

因此输入 payload 从 `17984 B` 变成 `13888P+4096 B`：P=2/4/8 为原来的
1.77/3.32/6.41 倍。这是逻辑搬运量；缓存命中/TMA multicast 可能减少实际 HBM 流量，不能直接
乘到运行时间上。序列很多、原 grid 已足够大时，再拆分可能仅增加重复加载和调度。
P=8 时每份 V=16；更细分还会进一步压缩 MMA 的有效宽度，需要相应改变 tile。

### D. 固定 worker 池、动态队列、长度排序

任务粒度如果仍是整条 sequence/head，软件队列最多改变任务分配与顺序，无法缩短最长链。
以任务成本 L_j=ceil(seq_len_j/16)、W 个理想等速 worker 表示，下界为：

```
makespan >= max(max_j L_j, sum_j L_j / W)
```

**反例一：只有 12 条长链。** 增加 worker 数或轮询次数不会产生第 13 条可执行链。
**反例二：一条特别长的链。** 其余 worker 结束后，动态队列仍然只能等待这条链。
**反例三：原 grid 已有按需调度。** 软件 atomic 队列和额外控制可能比官方整个 CTA 的硬件调度更贵。

长度排序可以改善某些排队尾部，但不是把长链本身切短。若改为若干 chunk 一个任务，再将状态
写回并重新入队，可让长链之间公平轮转，却会引入状态装载/存储、队列及跨任务依赖管理。
这个方案适合服务时延或混合工作负载，是否提高总吞吐需要独立实测。

### E. 2-CTA / thread-block cluster

应区分**两个普通 CTA 分别处理独立 value 分区**与 **tcgen05.cta_group::2 的协作 MMA**。
前者不需要 cluster 来维持数学正确性；后者需要架构支持、成对调度、TMEM/同步组织，可能利用
TMA multicast/协作数据搬运，但这些不会去掉状态的时间依赖。

对本讨论的 BF16 路线，cta_group::2 的整体 M 为 128/256、N 为 16 的倍数。
原方向 16×16 方阵如果放到 M=128，只剩 12.5% 有效算术；16×128 转置成 128×16 后才有
整除匹配。与讨论点 2 一样，先选对矩阵方向，再谈协作 MMA。

**反例一：任务仍少。** N=1、H=12，即使每条链用两块并行，参与的 CTA 也只有 24，
不能据此宣称利用满 148 个 SM。
**反例二：value 分区本来独立。** 强加每 chunk 的 cluster 同步可能比两个普通 CTA 更慢。
**反例三：合作扩大资源需求。** 小矩阵本来算术量少，成对 launch、barrier、共享输入组织的成本
未必能摊薄；需要同时比较等工作量的独立 2-CTA value-split 和真正 cta_group::2。

### F. 并行 affine scan：时间维并非数学上绝对不可并行

把单步写成 `S_t=A_t S_{t-1}+B_t`，其中
`A_t=(I-beta_t k_t k_t^T) diag(exp(g_t))`，`B_t=beta_t k_t v_t^T`。
两步变换可组合为 `(A2 A1, A2 B1+B2)`，组合在精确算术下可结合，因而能做前缀扫描。

**反例：计算结构改变。** 原本 rank-1/token 或 rank-16/chunk 的更新，组合后一般逐渐变稠密。
稠密 D×D 转移的组合涉及 D³ 工作；D=128、C=16 时，`D³/(CD²)=8`，这只是单项
算术量级对照，不是整个算法必然慢八倍。还需保存或重算变换、中间前缀及输出，且浮点运算
重排不保证与官方 BF16 状态舍入逐位一致。可以研究低秩/分层扫描，但已超出“换调度不动算法”。

## 4. 实测证据

正式运行：[metadata](results/metadata.json) · [全部计时](results/SUMMARY.md) · [节点资源](results/kernels.csv)。
B300（148 SM），Slurm job 25195，GPU UUID `GPU-ab0e8f8b-abe0-a03f-c8e9-65622211a5f4`。
35 个工作负载，每个 full/K1/K2 各五轮，共 525 行计时；35 个工作负载的隔离重放输出与最终状态
均和完整图逐位一致。CPU 代数验证为 30 组。
58 次 SM 时钟采样为 **1950–2032 MHz**，其中 48 次为 2032 MHz。未锁频；200 ms 采样
不能排除间隔内变化，因此几百分点的差异不单独用于判断方案优劣。

### 4.1 减少 head 数没有按比例降低单长链延迟

T_total=8192、N=1，单位 µs：

| H | K2 CTA 数 | K1 | K2 | full |
|---:|---:|---:|---:|---:|
| 12 | 12 | 42.202 | 744.010 | 788.493 |
| 24 | 24 | 75.494 | 744.198 | 821.738 |
| 48 | 48 | 141.402 | 746.429 | 890.499 |
| 96 | 96 | 273.677 | 750.429 | 1026.915 |

H 从 96 减至 12，工作量变成八分之一，K1 明显缩短，但 K2 仍约 744–750 µs。
这支持“长链延迟与有限独立任务数约束”的解释，不能据此直接认定 compute-bound 或 memory-bound；
讨论点 4 仍需硬件计数器。

### 4.2 更多独立序列有效，但收益不会无限增长

固定总 token=8192，改变等长独立序列数；下表仅 K2，单位 µs：

| N | 每序列 chunk 数 | H=12（CTA 数） | H=96（CTA 数） |
|---:|---:|---:|---:|
| 1 | 512 | 744.010（12） | 750.429（96） |
| 2 | 256 | 377.136（24） | 520.195（192） |
| 4 | 128 | 193.242（48） | 448.339（384） |
| 8 | 64 | 101.485（96） | 414.173（768） |
| 16 | 32 | 73.677（192） | 404.854（1536） |

H=12 时，N=1→8 的 K2 时间比为 7.33×；这比较的是合法独立序列工作负载，
不是把同一条序列切八段后的等价加速。H=96 时，N=8→16 的改善已很小；
增加 CTA 会遇到共享 SM 资源、调度波次和搬运等约束，不能按 N 线性外推。
所有测得的官方 K2 为 192 线程、98432 B 动态 shared memory，occupancy API 返回 2 CTA/SM。
这一驻留上限不是实际 achieved occupancy，也不意味着同时跑两个 CTA 时单个 CTA 的速度不变。

### 4.3 相同 CTA 数，长尾仍然显著

比较 varlen 路径的八条等长序列和 `[4608]+[512]*7`，总 token=8192、CTA 数相同。

| H | 等长 varlen K2 µs | 不均匀 K2 µs | 耗时比 |
|---:|---:|---:|---:|
| 12 | 102.038 | 420.234 | 4.12× |
| 24 | 138.646 | 581.203 | 4.19× |
| 48 | 231.722 | 587.363 | 2.53× |
| 96 | 402.733 | 720.144 | 1.79× |

H=12 时，等长的最长链是 64 chunks，不均匀的是 288 chunks，增长 4.5 倍；
实际 K2 时间增长 4.12 倍。只看 CTA 数会漏掉这个差异。
这两个实验都使用 varlen 路径，避免把变长索引开销误当成主要的长尾证据。
更大 H 的任务已有资源竞争，不能只用最长链比值预测时间。

### 4.5 调度模型用于反例，不作为 GPU 测速

以 148 个理想等速 worker、整条 sequence/head 为不可抢占任务，模型得到：

| 工作负载 | H | 下界 | FIFO | 最长任务优先 | 静态轮转 |
|---|---:|---:|---:|---:|---:|
| equal_n1 | 12 | 512.00 | 512 | 512 | 512 |
| skew8 | 12 | 288.00 | 288 | 288 | 288 |
| skew8 | 96 | 332.11 | 512 | 352 | 960 |
| ragged6 | 96 | 334.05 | 463 | 344 | 480 |

单位为模型中的 chunk 时间。12 条长链的 FIFO/长度排序/静态分配完全相同，说明队列不能消除关键路径。
96-head 不均匀工作负载上，长度排序可以改善理想队列尾部；但 GPU 并不保证使用这个 FIFO 次序，
两个驻留 CTA 也不是两个等速独立 SM，因此不能把模型比值当作 persistent 相对官方的实测加速。


## 5. 方案如何相互约束

| 场景 | 优先尝试 | 用什么反例否定过度承诺 |
|---|---|---|
| TP8、N=1，只有 12 条链 | value 分区，保持 chunk 顺序 | 多 head/CTA 反而减少 CTA；队列不能生成新链 |
| 多个独立短请求，NH 很大 | 适当 head 分组或任务常驻，减少小任务开销 | shared/寄存器膨胀，合并后驻留下降 |
| varlen 长短差异大 | 长任务优先、动态分配；必要时 value 分区 | 最长链下界不变；官方已有按需 CTA 调度 |
| 要使用 2-CTA tcgen05 | 先选无 padding 的矩阵方向，并与独立 value-split 对照 | 小方阵的 padding 更严重，协作成本可能没有收益 |
| 极长单链且局部拆分已用尽 | 评估 affine/低秩分层 scan | 额外算术、存储和状态舍入变化 |

对本题下一步实现的建议是 **先做 P=2/4/8 的 value-split K2，保留 K1 及 CHUNK=16**。
按 H=12/96、N=1/8、短/长/不均匀序列扫描；输出与最终状态均对拍，并测 full 与 K2。
若有收益，再比较输入 multicast、2-CTA 和跨链常驻调度，避免同时改多个因素而难以归因。

这里给出了候选、代数合法性、资源/调度反例与官方实测，不把尚未实现的候选说成已经获得加速。
